Working with AI: context, specifications and a verifiable result

How I organise agent-assisted work on this site: facts and requirements stay in the project, while readiness is checked separately from how convincing an answer sounds.

A workflow used in practice

OpenSpec, a fact register, automated checks and release records are used to develop this portfolio.

An example from this portfolio project. My role covers context, requirements, factual corrections and direction. AI agents also perform implementation and checks; I do not claim to have manually written every component.

From an idea to publication

Start with what must be preserved

When I share an experience or request a product change, the task is more than adding text to a page. Sources, constraints and decisions need to survive the conversation. I requested SDD and OpenSpec so that context remains in the project and is available to the next agent.

Specify before calling it done

A change describes its objective, design, requirements and acceptance scenarios. OpenSpec organises these as proposal, design, spec and tasks. A checked task helps track progress, but it does not prove a feature works. That requires verification of the built result.

Separate skills from product requirements

Instructions and skills describe how an agent works: what to read, how to verify outputs and what must remain private. Specifications describe the product requirements. I set constraints and clarify the content; the agent uses these materials during implementation. This keeps shared project rules available when a feature changes.

Review the result independently of its author

For the site, I requested separate editorial, UX and technical reviews, plus external technical review of an anonymous bundle. Checks also cover links, languages, PDFs and user scenarios. A review score is meaningful only with a defined scope and a specific version.

Keep decisions available for the next change

Sources, specifications and research archives are stored in private Git. The public site receives the built output. Hashes connect it to the reviewed version, and the live site is checked after deployment. This makes changes traceable without implying that the process eliminates every error.
