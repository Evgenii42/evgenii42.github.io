Checking more than code: Codex, OpenCode and output quality

We had written a PDF verifier, but the main build never ran it. A second agent found the gap. This is how I separate implementation from verification, and why one convincing model response is not enough.

Separate responsibilities, not just responses

While developing this portfolio, I set the objective, context and factual boundaries. Codex acts as the main orchestrator: it handles implementation and brings in subagents for separate editorial, UX and technical tasks. Another agent runs through OpenCode using a model served by Together AI. These are distinct process roles; their conclusions still need checking. I do not claim to have written every component myself.

Give the second agent a concrete review scope

We prepare selected templates, scripts and fictional data for external review. Biography, contacts and real PDFs are excluded. The reviewer can read and search the code but cannot edit the project or run a browser. It must identify the location, risk and evidence behind a finding. Browser tests, text extraction and visual PDF inspection remain separate tasks.

The check exists, but what runs it?

During the PDF update review, the second agent noticed that the new verifier checked text, fonts and links, yet the main build never called it. Having the test gave us an incomplete view of readiness. We wired it immediately after PDF generation and again after Hugo, including comparison of published files. Either failure now stops the build. This improves the release process; it does not establish that users had previously received broken files.

Make sure valid input can pass

The link tests had another gap. They rejected bad inputs without proving that good input was accepted: a function rejecting everything could have passed that suite. We added positive controls and checks for blank labels and malformed records. We also strengthened the legacy link branch to verify the destination page in the selected language. The final set includes four valid calls and ten invalid inputs.

The reviewer also needs verification

Some findings concerned fictional fixtures and the description of the anonymous packet rather than the public product. We handled those separately, aligning identifiers and clarifying that generic technical terms were not personal profile data. A follow-up review checked the fixes. The project also records a different lesson: I first noticed the filter styling problem as a user, after which the agents added appearance and geometry checks. Static reading alone had not been enough.

Judge the result, not the score or agent count

After the fixes, we rebuilt and compared the final files. All four PDFs retained the text, links and raster output of their ten pages. Reports remain tied to specific versions, and earlier findings stay in the record. We aim to control cost by limiting context and repeating checks relevant to the changed scope. More agents do not automatically mean lower cost: we have not measured a comparison with a single-model workflow.
