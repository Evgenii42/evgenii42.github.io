Test the flow before the next release: web prototypes and AI agents

An idea is easier to discuss when you can walk through it. At EmTalk, I organise bounded web increments: I define behaviour and limits, then connect agent work through SDD, OpenSpec and checks of the built result.

Workflow applied to web increments

Guest BRET and DM flows progressed from requirements to browser checks and publications. PWA remains a near-term plan, not an implemented feature.

From an idea to a testable flow

  1. Task and increment boundaries
  2. Source behaviour and constraints
  3. SDD and OpenSpec scenarios
  4. Implementation with agents
  5. Failures, browsers and preview
  6. Decision on the next step

Limit the experiment to a complete action

For the first web versions, I selected guest exercises without mandatory registration or AI. This focused work on the core behaviour: completing a practice or working through decision options. Authentication, payments and cloud features stayed outside the increment. That gave us something concrete to walk through and test.

Use source behaviour rather than memory

Agents inspected the current Android sources and transferred behaviour from recorded revisions. For BRET, phases, elapsed time, pause and resume matter. For DM, the comparison rules, calculations, saving and recovery matter. I provide product context and choose the scope of the port; this does not mean I manually wrote every component.

Give agents a durable contract

SDD and OpenSpec capture the goal, design, requirements, scenarios and tasks. Project instructions and skills explain how an agent should use those materials and checks. I can refine the idea without losing agreed constraints. Local saving must not turn into a promise of cloud sync, and a notice about future AI must not become a non-working button.

Test behaviour, including failures

DM's calculation model is separated from its interface and storage; BRET's practice timer is separated from DOM and audio control. We can check rules independently and then walk through the complete browser flow. The project examined corrupted saves, denied storage, pause, audio failures, import and export. A preview supports discussion of real behaviour; passing a technical test does not prove demand or user understanding.

Publication does not end verification

Source code, builds, reports and publications are connected through versions and hashes. The deployed site needs separate checks: actual hosting and browsers can behave differently from the local environment. Failed checks and unresolved findings are retained. An intermediate version remains intermediate even when it is available to view.

PWA as the next testable step

I am considering PWA as a near-term step, giving people an app-like way to return to a tool. It is currently an idea, not a completed user experiment or an installable/offline release. I want to test the core flow and repeat need first, then choose the platform capabilities required. A web prototype lets us investigate behaviour before taking on the full scope of the next format.
